Commit reviewed changes and push to `main`. The `Portfolio checks` workflow runs automatically on pushes and pull requests. GitHub Pages uses the existing branch deployment; verify both checks and the `pages build and deployment` run for the published commit, then inspect the live home page, a room deep link, reading page, résumé, sharing card, and sitemap.

After Pages finishes for the exact release commit, run `node scripts/verify-live.mjs --record` to compare the canonical live pages, runtime content/routing/model/style modules, binary assets, sitemap, crawler setup and release documentation against committed `HEAD`. Text comparisons normalize Windows line endings; Raster-image/PDF comparisons use exact bytes. The command records the verified content release in `state/deployment.json`. Commit this evidence and its QA/roadmap closeout separately, wait for CI and Pages for that evidence commit, then run `node scripts/verify-live.mjs` without `--record` to verify final HEAD. The recorded content-release SHA intentionally remains the first commit; do not repeatedly rewrite the record to chase its own evidence commit. Save the final read-only result in ignored `.preview/` and link the matching successful workflows in the release closeout.

For a regression, use `git revert <commit>` and publish the revert through the same checks. This preserves history and provides a reproducible rollback. `node_modules/` and `.preview/` are local-only and stay ignored.

Periodic content review is ongoing maintenance: revisit project status, experience, résumé, external links, demos, and measured results when they change. No unattended account changes or recurring notification jobs are configured.
